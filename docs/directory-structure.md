# Directory structure

This page describes what each file and folder means — both inside a Vulse-powered project and inside this monorepo.

## In a Vulse-powered Astro project

After running `pnpm astro add @vulsecms/core` and `pnpm astro add cloudflare`, your project looks roughly like:

```
my-site/
├── astro.config.mjs              Astro config; imports vulse/integration
├── wrangler.toml                 Cloudflare bindings (DB, BUCKET, FORM_QUEUE, vars/secrets)
├── tsconfig.json                 Includes .astro/types.d.ts and .vulse/types.d.ts
├── package.json                  Workspace + vulse + @astrojs/cloudflare deps
├── src/
│   ├── content.config.ts         Optional Content Layer loaders (empty by default; use --static scaffold)
│   ├── pages/                    Your Astro pages
│   │   ├── index.astro
│   │   ├── sign-in.astro         (your own auth page using vulse/client/components)
│   │   └── blog/
│   │       ├── index.astro       Generated by `vulse collection:scaffold`
│   │       └── [slug].astro      Generated by `vulse collection:scaffold`
│   └── vulse/
│       └── collections/          Code-defined blueprints
│           ├── page.ts           Created by the install hook
│           └── post.ts           Your own blueprints
└── .vulse/
    └── types.d.ts                Generated types for your collections (don't edit by hand)
```

### `astro.config.mjs`

```js
import { defineConfig } from 'astro/config'
import cloudflare from '@astrojs/cloudflare'
import vulse from '@vulsecms/core/integration'

export default defineConfig({
  output: 'server',
  adapter: cloudflare({ platformProxy: { enabled: true } }),
  integrations: [vulse()],
})
```

> For production deploys, add a `configPath: process.env.WRANGLER_CONFIG` option to the adapter so builds can target `wrangler.production.toml` without overwriting `wrangler.toml`. See [installation.md](installation.md#1-prerequisites) and [deployment.md](deployment.md).

The integration:

- Mounts admin pages under `/admin`.
- Mounts the REST API under `/api/vulse/*` and `/api/auth/*`.
- Registers a middleware that resolves the staff session for each request.
- Writes `.vulse/types.d.ts` on `astro:config:setup`.

### `wrangler.toml`

Required bindings (see [`configuration.md`](configuration.md)):

- `DB` (D1) and `BUCKET` (R2) — required.
- `FORM_QUEUE` (Queue) — optional, enables async form processing.
- `[vars]` / wrangler secrets — `BETTER_AUTH_SECRET`, `VULSE_PREVIEW_SECRET`, `CF_IMAGES_*`.

### `src/content.config.ts`

Created empty on install. Collection pages use the **runtime SDK** by default (`collection:scaffold` generates SSR index/show templates). To opt into build-time `getCollection()` for a collection, run `npx vulse collection:scaffold <handle> --static` or add `vulseLoader()` entries manually — see [`frontend.md`](frontend.md).

### `src/vulse/collections/`

One file per code-defined blueprint. The integration scans this directory and merges with blueprints created at runtime in the admin (which live in the `vulse_collections` table).

```ts
// src/vulse/collections/post.ts
import { defineCollection, z, blocks, media } from '@vulsecms/core'

export default defineCollection({
  name: 'post',
  label: 'Blog post',
  schema: z.object({
    title: z.string().min(1),
    slug: z.string(),
    body: blocks(),
    cover: media().optional(),
  }),
  admin: { titleField: 'title', listColumns: ['title', 'slug'] },
})
```

### `.vulse/types.d.ts`

Generated TypeScript types for your collections. Include it in `tsconfig.json`:

```json
{ "include": [".astro/types.d.ts", ".vulse/types.d.ts", "**/*"] }
```

It is regenerated on every `astro:config:setup` (so dev-server start, `astro build`, etc.).

### `src/pages/`

Your normal Astro pages. The scaffold CLI drops generated detail/list pages here, but they are yours to maintain afterwards.

### `packages/vulse/src/core/`

Domain layer. No HTTP, no R2, no auth — just the data model and rules.

```
core/
├── db.ts                         createDb() — Drizzle on D1
├── schema.ts                     Drizzle schema for every Vulse table
├── access.ts                     Access-rule evaluator
├── errors.ts                     VulseError + ValidationError / NotFoundError / ...
├── locales.ts                    Locale settings helpers
├── parse-content.ts              Zod runner that produces humanized issues
├── preview-content.ts            resolvePreviewContent() — picks live/draft/published
├── slug.ts                       Slug normalisation + validation
├── migrations.ts                 Applies the bundled SQL at runtime
├── blueprints/                   Blueprint helpers (definition, compile, mutations, ...)
├── blocks/schema.ts              Block-node schema
├── forms/                        Form definition + queue/unique-value/rate-limit logic
├── globals/                      Global definition + compile
├── repos/                        Data-access classes
│   ├── entries.ts                EntriesRepo — i18n-aware CRUD over entries + entry_locales
│   ├── revisions.ts              RevisionsRepo
│   ├── preview-sessions.ts
│   ├── media.ts
│   ├── forms.ts
│   ├── globals.ts
│   └── settings.ts
└── sets/                         Reusable-set definition + compile
```

### `packages/vulse/src/server/`

HTTP layer. Routes wrap the repos with auth + access checks and return the standard `ok` / `fail` envelope.

```
server/
├── handler.ts                    defineHandler() — typed Zod-validated handlers
├── envelope.ts                   ok() / fail() helpers
├── runtime.ts                    getRuntime() — wires routes, auth, SDK
├── env.ts                        Reads Cloudflare bindings
├── better-auth.ts                Better Auth setup
├── preview.ts                    Preview cookie signing
├── cron.ts                       vulseScheduled() — purge handler
├── r2.ts                         R2 helpers
├── cf-images.ts                  Cloudflare Images integration
├── image-probe.ts                Read width/height from uploaded images
├── loader.ts                     vulseLoader() — Astro Content Layer
├── assets/
│   └── live-preview-bridge.js    Bundled live-preview shim served at /api/vulse/preview/bridge.js
├── forms/                        Submission processing, queue glue, email
├── sdk/                          Server SDK (createSdk, collections, search, media)
├── routes/                       One file per resource (entries, sets, globals, ...)
└── endpoints/                    Thin Astro APIRoute glue — one per URL pattern
```

### `packages/vulse/src/client/`

Public rendering and browser-side auth. Anything here can be imported from a user's Astro project.

```
client/
├── BlockRenderer.astro           Server-side block renderer
├── BlockRenderer.vue             Vue block renderer (custom sets)
├── ProseMirrorRenderer.vue
├── Node.vue
├── render-pm-html.ts
├── pm-types.ts, pm-defaults.ts   ProseMirror typing
├── url.ts                        URL helpers
├── inject.ts                     Block-node component registry
├── embed.ts                      OEmbed helpers
├── auth.ts                       Browser auth SDK
├── live-preview-bridge.ts        Source of the bridge bundle (built into server/assets)
├── components/                   Astro components (SignInForm, SignUpForm, ...)
└── blocks/                       One Vue component per built-in block node
```

### `packages/vulse/src/admin/`

The Vue admin UI.

```
admin/
├── pages/                        Astro pages mounted under /admin
├── components/                   Vue components and the AdminShell
├── client/                       Admin-side helpers (api client, field reflectors)
├── styles/admin.css
└── assets/                       Logo and other static assets
```

### `packages/vulse/migrations/`

```
migrations/
├── 0000_init.sql                 Core tables, Better Auth, entries + entry_locales, FTS
├── 0001_collections_sets.sql     Runtime schema editor tables
├── 0003_fts.sql                  FTS5 virtual table + triggers
├── 0004_forms.sql                Forms, submissions, upload drafts, rate limits
├── 0005_globals.sql              Global sets and values
├── 0006_preview_sessions.sql     Live preview sessions
├── 0007_redirects.sql            Redirects
└── 0008_two_factor.sql           Better Auth two-factor table
```

Migration `0002_tree_drafts` was folded into `0000_init` when the i18n schema split was introduced. The ledger ID is intentionally skipped to keep history forward-only.

Migrations are hand-written, forward-only SQL (`NNNN_name.sql`) applied with `wrangler d1 migrations apply` — never rename an existing file, since wrangler's ledger tracks them by filename. When adding a migration, update `src/core/schema.ts` to match; the schema-drift integration test fails CI if the two disagree.

### `playground/vulse-play/`

A working Astro project that depends on the local `vulse` package via `workspace:*`. Use it to develop and exercise changes:

```bash
pnpm install
pnpm --filter @vulsecms/core build
cd playground/vulse-play
npx vulse migrate
pnpm dev
```

### `docs/superpowers/`

Internal design specs and implementation plans. Not part of the user-facing docs; safe to read for context if you're contributing.
